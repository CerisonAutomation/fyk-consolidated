# Environment Variable Security Audit

Generated: 2026-09-11

## Overview

This document classifies every environment variable in the project by exposure
level, documents its security posture, and recommends a key rotation schedule.

**Golden Rule**: Any variable with a `VITE_` prefix is inlined into the client
JavaScript bundle by Vite and must be treated as **public**. All other variables
are **server-only** and must never reach the browser.

## Client-Safe Variables (VITE_ prefix — inlined into bundle)

These are accessible via `import.meta.env.VITE_*` in browser code. Vite
inlines them at build time. They are **public by design**.

| Variable | Purpose | Security Status |
|---|---|---|
| `VITE_SUPABASE_URL` | Supabase project URL | SAFE — public endpoint |
| `VITE_SUPABASE_ANON_KEY` | Supabase anon key | SAFE — protected by RLS. The existing `env.ts` already guards against accidentally shipping a service_role key. |
| `VITE_MAPBOX_ACCESS_TOKEN` | Mapbox static tiles | SAFE — public token scoped to account |
| `VITE_VAPID_PUBLIC_KEY` | Web Push subscription | SAFE — public key, cannot decrypt |
| `VITE_ENABLE_DEMO` | Feature flag | SAFE — boolean |
| `VITE_ENABLE_UPLOADS` | Feature flag | SAFE — boolean |
| `VITE_ENABLE_PRECISE_LOCATION` | Feature flag | SAFE — boolean |
| `VITE_ENABLE_EVENT_CREATION` | Feature flag | SAFE — boolean |
| `VITE_ENABLE_BILLING` | Feature flag | SAFE — boolean |

### Mapbox Token Note

`VITE_MAPBOX_ACCESS_TOKEN` is a public token (`pk.*`). Mapbox public tokens
are designed to be embedded in client code. However:
- Set referrer restrictions in your Mapbox dashboard
- Monitor usage for unexpected spikes
- Rotate if compromised

### Supabase Anon Key Note

The Supabase anon key is public by design — it grants exactly what Row Level
Security (RLS) policies allow and nothing more. The existing guard in
`src/integrations/supabase/env.ts` (lines 53-75) correctly detects and blocks
a `service_role` key from being shipped to the client.

## Findings

### 1. VITE_ vars are safe (no sensitive data exposure)

All `VITE_` prefixed variables in the client bundle are either:
- **By design public**: Supabase anon key, Mapbox token, VAPID public key
- **Boolean feature flags**: No sensitive data

**No critical findings.** No secrets are being exposed to the client bundle.

### 2. Monitoring file uses `process.env` for public analytics key

`src/lib/monitoring.ts` (line 70) uses `process.env.NEXT_PUBLIC_POSTHOG_KEY`
rather than a `VITE_` variable. This works in TanStack Start server contexts
but will be `undefined` in browser code. This is not a security issue — PostHog
keys are designed to be public — but it is an inconsistency with the `VITE_`
convention used elsewhere. Consider migrating to `VITE_POSTHOG_KEY` if PostHog
needs to run in the browser.

### 3. `.env.example` was missing several required variables

The original `.env.example` was missing:
- `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (required by the app)
- `VITE_MAPBOX_ACCESS_TOKEN` (required by map features)
- `SUPABASE_ACCESS_TOKEN` (used in `.env.local`)
- `NEXT_PUBLIC_POSTHOG_KEY` / `NEXT_PUBLIC_POSTHOG_HOST`

**Fixed** in the updated `.env.example`.

## Rotation Schedule

| Frequency | Variables |
|---|---|
| **90 days** | `SUPABASE_SERVICE_ROLE_KEY`, `AUTH_SECRET`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `STRIPE_SECRET_KEY`, `UPSTASH_REDIS_REST_TOKEN`, `RESEND_API_KEY`, `VAPID_PRIVATE_KEY`, `SUPABASE_ACCESS_TOKEN` |
| **180 days** | `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `STRIPE_PUBLISHABLE_KEY`, `SENTRY_DSN`, `NEXT_PUBLIC_POSTHOG_KEY`, `VAPID_SUBJECT` |
| **On personnel change** | All server-only variables |
| **Immediately** | Any key suspected of exposure |

### Rotation Procedure

1. Generate new key at the provider (e.g., Supabase dashboard, Stripe dashboard)
2. Update `.env.local` with the new value
3. Redeploy all environments
4. Verify the old key is revoked (if provider supports it)
5. Update this document's "Last Rotated" dates

## Checklist for New Environment Variables

Before adding a new env var, ask:

- [ ] Does it contain a secret? If yes, **no VITE_ prefix**
- [ ] Is it only needed server-side? If yes, **no VITE_ prefix**
- [ ] Is it safe to expose in the client bundle? If yes, use `VITE_` prefix
- [ ] Is it documented in `.env.example`?
- [ ] Is it validated in `src/lib/env-validation.ts`?
- [ ] Have you added it to this security audit document?
